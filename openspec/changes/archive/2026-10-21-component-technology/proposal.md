# Proposal

## Why

Диаграмма C4 Component сейчас несёт только описание компонента, поэтому по ней нельзя понять, на чём он
реализован (`ASP.NET Core`, `PostgreSQL`, `RabbitMQ`). C4 предусматривает для этого отдельную строку
технологии, но атрибут `C4Component` её не предоставляет — разметить технологию нечем.

Попутно вскрылась проблема в существующем тексте диаграммы: рендерер выводит описание третьим позиционным
аргументом макроса `Component(alias, label, techn, descr, ...)`, то есть в слот **технологии**, а не
описания. В C4-PlantUML технология рисуется курсивом в квадратных скобках, описание — отдельным блоком.
Сейчас все описания рендерятся как технология, а добавить настоящую технологию, не исправив это,
невозможно: свободного слота в макросе нет.

## What Changes

- **BREAKING** (текст диаграммы): макрос компонента получает форму
  `Component(alias, name, technology, description)`. Описание переезжает из слота технологии в слот
  описания; при отсутствии технологии выводится пустая строка `""`. Меняется внешний вид всех
  существующих диаграмм: описание перестаёт быть курсивной строкой в квадратных скобках и становится
  обычным блоком под названием.
- `C4ComponentAttribute` получает необязательный третий параметр конструктора `technology` и свойство
  `Technology` только для чтения:
  `C4ComponentAttribute(string description, bool isRoot = false, string? technology = null)`.
- Технология проходит пайплайн целиком: читается из атрибута, попадает в дерево вызовов, затем в модель
  диаграммы и в текст `.puml`.
- Технология класса и технология метода независимы: значение берётся только из собственного атрибута узла
  и от класса к методу не передаётся.
- Версия пакета разметки поднимается `3.0.0 → 3.1.0`: добавляется необязательный параметр конструктора, и
  ранее скомпилированная разметка продолжает компилироваться. Версия CLI поднимается `1.2.0 → 2.0.0`:
  меняется содержимое диаграммы. CLI 2.0.0 поставляется вместе с атрибутами 3.1.0 — эта пара фиксируется
  как соглашение о релизе.
- Типизация компонентов перестаёт быть автоматической по имени: цветовой тег `repository`/`gateway`
  выводится из значения технологии, а не из подстроки в имени компонента.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `c4-annotation-attributes`: контракт атрибута `C4Component` расширяется необязательным параметром
  конструктора `technology` и свойством `Technology`.
- `component-diagram-generation`: требование к структуре текста фиксирует новую форму макроса
  `Component(alias, name, technology, description)` и правило вывода пустой технологии.

## Не входит в объём

- Автоматическое определение технологии по имени проекта, пространству имён, ссылкам на пакеты или типу
  компонента. Значение задаётся только разметкой.
- Изменение набора цветовых тегов и их цветов: правило выбора тега переезжает с имени компонента на
  технологию (см. «What Changes»), но сами теги `repository`/`gateway` и их палитра остаются прежними.
- Атрибуты `C4Context`, `C4Container`, `C4Code` остаются объявленными и не влияющими на результат.
- Экранирование кавычек и служебных символов в описании и технологии — существующий пробел, не
  затрагивается.
- Наследование технологии от класса к методу и наследование сверх действующего правила «описание берётся
  от класса-реализации, интерфейс — только если реализации нет».

## Влияние на публичный контракт

Меняются обе публичные поверхности, поэтому изменение оформлено отдельным change с дельтой спек.

- **Атрибуты.** Новый необязательный параметр конструктора меняет метаданные конструктора
  `C4ComponentAttribute`. Ранее скомпилированная разметка продолжает компилироваться без правок, поэтому
  подъём мажорной версии не требуется: спека формулирует совместимость в терминах компиляции разметки, а
  добавление необязательного параметра её не нарушает. Отдельно фиксируем: потребитель, собранный против
  3.0.0 и не пересобранный, при инстанцировании атрибута получит ошибку отсутствующего метода
  конструктора. Для этого инструмента такой сценарий практически не встречается — анализ идёт по
  исходникам через Roslyn `MSBuildWorkspace`, и без пересборки целевого проекта диаграмма всё равно не
  изменится. Это осознанное решение, а не недосмотр. Компенсировать разрыв не чем: технология должна
  сочетаться с `isRoot` на одном атрибуте, а вариант с `{ get; set; }` недоступен из-за C# 8 в проекте
  атрибутов и нарушает неизменяемость свойств.
- **Текст диаграммы.** Форма макроса `Component` входит в контракт содержимого, поэтому её смена требует
  дельты `component-diagram-generation` и подъёма версии CLI до `2.0.0`. Отдельно меняется правило выбора
  цветового тега: он выводится из технологии, а не из имени компонента. Порядок строк и пробелы контрактом
  не являются и требованием не закрепляются.
- **Публичный API библиотеки.** Конструктор `InvocationTree` получает третий необязательный параметр.
  Спеками публичный API не покрыт (зафиксировано в `AGENTS.md`), но границы слоёв сохраняются: технология
  передаётся только через модели в `C4ModelBuilder.Models/Analysis`.
- **Согласованность релизов.** CLI публикуется образом, а атрибуты — пакетом NuGet, и пакетной
  зависимости между ними нет: CLI получает атрибуты транзитивно через ссылку на анализатор. Поэтому пара
  «CLI 2.0.0 поставляется с атрибутами 3.1.0» фиксируется как соглашение о релизе и указывается в README,
  а не как ребро графа зависимостей.

## Impact

- `C4ModelBuilder.Attributes/C4ComponentAttribute.cs` — параметр конструктора, свойство, пример в
  XML-документации; версия пакета в `C4ModelBuilder.Attributes.csproj`; примеры в
  `C4ModelBuilder.Attributes/README.md`.
- `C4ModelBuilder.Models/Analysis/InvocationTree.cs` — перенос технологии в дереве вызовов.
- `C4ModelBuilder.Analyzer/Infrastructure/AttributeDataExtensions.cs` — чтение технологии из атрибута;
  существующие чтение описания и признака `isRoot` не меняются.
- `C4ModelBuilder.Analyzer/Models/InvokedMethod.cs`, `MethodAnalyzer.cs`, `SolutionAnalyzer.cs` — передача
  технологии в узлы дерева.
- `C4ModelBuilder.PlantUmlCreator/C4ComponentDiagram.cs`, `InvocationTreeMerger.cs`, `PlantUmlRenderer.cs` —
  перенос технологии в модель диаграммы, вывод её в текст и выбор цветового тега по технологии вместо имени.
- Тесты: `PlantUmlRendererTests`, `PlantUmlGeneratorTests` (форма макроса), `InvocationTreeMergerTests`
  (перенос технологии и выбор тега по ней), `SolutionAnalyzerTests` (чтение из разметки).
- `README.md` (раздел «Разметка», соглашение о парных версиях), `C4ModelBuilder.Cli.csproj` — версия CLI
  `2.0.0`; `AGENTS.md` — правило типизации и шкалы версий.
- Спеки: `openspec/specs/c4-annotation-attributes/spec.md`,
  `openspec/specs/component-diagram-generation/spec.md`.
