# Design

## Context

Поток CLI сейчас: `Program.cs` (top-level) → `CliArgumentsParser.Parse(args)` → `CliOptions` → DI →
`C4Builder.Run`. Разбор собирает `RootCommand` из семи опций и **до** обращения к действию руками
читает обязательные значения (`GetRequiredValue(solutionOption)`), поэтому документально
предусмотренное поведение `System.CommandLine` не работает: `VersionOption` описан как «short circuit
normal command handling and instead write out version information before exiting», но короткое
замыкание отменяет только проверку обязательных опций, а не наш ручной вызов — в итоге
`InvalidOperationException` и код `-532462766` (замерено на `--version`, `--help`, `-h`).

Ограничения, влияющие на решение:

- `System.CommandLine 2.0.12`: публичны `VersionOption`, `Help.HelpAction`, `ParseResult.Action`,
  `Command.SetAction(Func<ParseResult, CancellationToken, Task<int>>)` и
  `ParseResult.InvokeAsync(InvocationConfiguration, CancellationToken)` («returns a task whose result
  can be used as a process exit code»).
- Сборка: `C4ModelBuilder.Cli.csproj` не задаёт `<Version>` → SDK-дефолт `1.0.0`;
  `dotnet msbuild -getProperty:Version` возвращает `1.0.0`, у `Attributes.csproj` — `3.0.0`.
- Прецедент релиза атрибутов: отдельный коммит `d00497d` («повышена версия проекта») + тег `v3.0.0`;
  пространство тегов `vX.Y.Z` занято пакетом разметки.
- Поставка: `Dockerfile` публикует без параметра версии и не ставит меток; `publish-cli-docker.yml`
  пушит статический `:latest`; `.dockerignore` исключает `**/.git`, поэтому внутри образа
  git-истории нет.
- Тестов CLI в решении нет; по AGENTS.md поведение CLI подтверждается инспекцией и прогоном, а не
  юнит-тестами.

## Goals / Non-Goals

**Goals:**

- Единый номер версии CLI, наблюдаемый и в сборке (`FileVersion`/`InformationalVersion`), и в
  `--version`, и в теге/метаданных образа.
- Флаги `--version`, `--help`, `-h` работают по спецификации `cli-tool` (код `0`, анализ не идёт).
- Записанное правило двух шкал версий и порядок релиза CLI.

**Non-Goals:**

- Версия внутри `.puml` — генератор остаётся чистой функцией «дерево → текст».
- Автовывод версии из git; единая шкала с атрибутами; версии непубликуемых проектов.
- Новый тест-проект CLI и выделение тестируемого шва в парсере — отдельное изменение.

## Decisions

**D1. Источник версии — явный `<Version>1.1.0</Version>` в `C4ModelBuilder.Cli.csproj`.**
Альтернативы: MinVer/GitVersion (новая зависимость по AGENTS.md требует обоснования, нужна
git-история в сборке образа, а `.dockerignore` её исключает, плюс конфликт префиксов тегов с `v*`
атрибутов); `github.run_number` (номер не связан с кодом); `Directory.Build.props` (лишний уровень
косвенности на одно свойство). Выбор согласуется с прецедентом атрибутов и не добавляет зависимостей.
Побочно: `InformationalVersion` в образе будет без `+sha` (git-истории там нет), то есть `--version`
внутри контейнера печатает ровно `1.1.0`, а локальная сборка — `1.1.0+<sha>`; оба варианта
удовлетворяют сценарию «в выводе присутствует `X.Y.Z`».

**D2. Две шкалы: атрибуты — версия контракта разметки (`3.x`), CLI — версия поведения инструмента
(`1.x`).** Правка только поведения CLI или содержимого диаграммы бампает CLI и не двигает атрибуты:
иначе релиз пакета уходил бы без изменений в пакете. Теги CLI — с префиксом `cli-vX.Y.Z`, чтобы не
занимать `v*`. Правило и порядок релиза (коммит с bump-ом → тег → диспатч `publish-cli-docker.yml`)
фиксируются в `AGENTS.md`, кратко — в README.

**D3. Флаги версии и справки отдаются библиотеке, а не пишутся руками.** Команда получает действие
через `SetAction(Func<ParseResult, CancellationToken, Task<int>>)`, а `Program` вызывает
`parseResult.InvokeAsync(...)` и возвращает полученный код: при `--version`/`--help` библиотека сама
выводит текст и код `0`, при ошибке разбора — сообщения и код `1`, при обычном запуске — наше
действие. Альтернатива «оставить ручной `Parse` и опознавать `ParseResult.Action`/`VersionOption`»
требует знания внутренних типов действий, дублирует логику библиотеки и не даёт бесплатной справки;
альтернатива «своя опция + ручной `Console.WriteLine`» даёт полный контроль формата, но теряет
сгенерированную справку и добавляет код на то, что библиотека делает сама. Формат вывода остаётся
неподконтрактным: спека требует лишь наличие номера версии и перечня параметров.

**Структура точки входа (уточнено при ревью).** Разбор — подчинённый шаг `Program.Run`: действие
команды назначает сам `Run` перед вызовом `Parse`, а `CliArgumentsParser` описывает поверхность команды
(`CreateRootCommand()`) и читает значения (`ReadOptions(ParseResult)`), не зная ни о пайплайне, ни о
токене отмены. Так главная функция не передаётся в парсер аргументом: `SetAction` требует действия до
`Parse`, но кто его назначает — решает вызывающий код. Единственный `CancellationTokenSource` создаётся
на верхнем уровне и подписан на `Console.CancelKeyPress`; `BuildServiceProvider` его больше не
подписывает, связанного источника нет.

**Дополнение по факту реализации (отступление от «флаги целиком на библиотеке»).** Сочетание
`--version` с другими параметрами библиотека **отвергает сама**: `VersionOption.AddValidators()` добавляет
ошибку `{0} option cannot be combined with other arguments.`, — но действие версии объявлено с
`ClearsParseErrors => true` и потому молча подавляет и эту ошибку, и ошибки остальных валидаторов
(замерено: `--version -s missing.sln -o output` → версия и код `0`). Спека требует сообщение и код `1`,
поэтому `Program` перед `InvokeAsync` проверяет `Errors.Count > 0 && Action is not ParseErrorAction` и
печатает ошибки через `ParseErrorAction` — тот же путь и текст, что у прочих ошибок разбора. Своей
детекции токенов и своего формата версии не потребовалось; `--help`/`-h` с другими параметрами ошибок не
порождают (`errors = 0`) и сохраняют библиотечное поведение.

**D4. Коды возврата и обработка исключений сохраняются как есть.** Тело действия повторяет текущую
логику (`try` / `catch TaskCanceledException` → `130` / `catch Exception` → лог и `1`), поэтому
дефолтный обработчик исключений библиотеки не задействуется. Ошибки разбора (отсутствующий
`--solution`, несуществующий файл, расширение не `.sln`) выводит библиотека в поток ошибок с кодом
`1` — совпадает с текущим контрактом «сообщение об ошибке + код `1`».

**D5. Версия в образе: `build-arg` + метка, а не только тег.** Workflow читает версию из
`C4ModelBuilder.Cli.csproj` (`dotnet msbuild -getProperty:Version`) и передаёт её в сборку; `Dockerfile`
принимает `ARG VERSION` (с дефолтом для локальной сборки), объявляет `org.opencontainers.image.version`,
`org.opencontainers.image.revision` (из `$GITHUB_SHA`, если задан) и передаёт `/p:Version=$VERSION` в
`dotnet publish`, чтобы номер в метке и номер в сборке не могли разойтись. Альтернатива «метка из
build-arg, сборка — из csproj»: две точки входа для одного номера, возможен дрейф. Публикуются теги
`:X.Y.Z` и `:latest`; повторный диспатч на уже существующий тег не перезаписывает его — версию
поднимают.

**Границы слоёв.** Изменения затрагивают только слой CLI (`C4ModelBuilder.Cli`) и поставку
(`Dockerfile`, workflow). `C4ModelBuilder.Models`, `C4ModelBuilder.Analyzer` и
`C4ModelBuilder.PlantUmlCreator` не меняются: `PlantUmlGenerator.Generate` остаётся чистой функцией,
версия в диаграмму не попадает. Новых зависимостей нет — используется уже подключённый
`System.CommandLine`.

## Risks / Trade-offs

- [Точный формат вывода `--version` задаёт библиотека и он может измениться при её обновлении] →
  спека требует лишь наличие номера версии; проверка в задачах сверяет наличие `1.1.0`, а не строку
  целиком.
- [Перевод точки входа на `SetAction`/`InvokeAsync` меняет того, кто пишет сообщения об ошибках
  разбора] → в задачах регресс-прогоны текущих сценариев: запуск без параметров, несуществующий
  `.sln`, чужое расширение, успешный прогон примера (`scripts/Invoke-Sample.ps1`), сверка кодов
  `0`/`1`.
- [Сигнатуры `InvokeAsync`/`InvocationConfiguration` этим изменением ещё не компилировались] → первая
  задача — компиляция и прогон; при несовпадении берётся синхронный `Invoke(InvocationConfiguration)`
  и код возврата действия.
- [Живой прогон публикации образа возможен только намеренным диспатчем, который реально публикует
  теги] → локально проверяются `docker build --build-arg` и метаданные через `docker inspect`; сам
  диспатч помечается как проверка, недоступная до релиза.
- [Нет тестов CLI] → проверка командой и запись этого ограничения в задачах; полноценный проект
  тестов — отдельное изменение.

## Migration Plan

Несовместимых изменений и миграции данных нет. Порядок релиза: коммит с bump-ом `<Version>` → тег
`cli-v1.1.0` → диспатч `publish-cli-docker.yml` → появляются теги `:1.1.0` и `:latest`. Откат —
реверт коммита; уже опубликованные теги остаются и не перезаписываются.
