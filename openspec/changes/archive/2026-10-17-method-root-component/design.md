# Design

## Context

См. `proposal.md` — Why. Существенное для подхода состояние пайплайна:

- `SolutionAnalyzer.AnalyzeComponents` перебирает `ParsedSolution.AllClasses`, оставляет классы, у которых
  `C4Component.IsRoot` истинно, создаёт `InvocationTree` с именем класса и вкладывает в него деревья
  публичных методов (`MethodAnalyzer.AnalyzeMethod`, `currentDepth: 0`).
- `MethodAnalyzer.AnalyzeMethod` уже формирует узел метода с именем `ClassMethod.Name` = `{Class}.{Method}`
  и описанием из атрибута `C4Component` этого метода; там же проверяется лимит `currentDepth > maxDepth`.
- `InvocationTreeMerger.MergeToComponentDiagram` не различает вид корня: начинает обход с `(root, null)`
  и делает корень компонентом, если у него есть описание. `PlantUmlRenderer` и `C4Builder` используют
  `NodeName` как псевдоним компонента и как имя файла.

Отсюда граница изменения: меняется обнаружение корней в `SolutionAnalyzer` и правило построения дерева
корня-метода во внутреннем `MethodAnalyzer`; `Models`, `PlantUmlCreator` и `Attributes` не затрагиваются.

## Goals / Non-Goals

**Goals:**

- Метод с `isRoot = true` даёт самостоятельную диаграмму, корневой узел которой — сам метод.
- Обнаружение корней остаётся в `SolutionAnalyzer`, без новых зависимостей и без изменения публичных
  сигнатур библиотеки.
- Поведение классовых корней сохраняется без изменений.

**Non-Goals:**

- Повторное использование результатов анализа, если корнем помечены и класс, и его метод (кэш не вводим).
- Изменение `ClassMethod`, `ParsedSolution`, `InvocationTree` и их API.
- Диагностика игнорируемой разметки и отбор корней по видимости.

## Decisions

### D1. Корневой узел — сам метод, без узла-класса

Дерево корневого метода — это узел, который возвращает `AnalyzeMethod` для этого метода: `NodeName` =
`{Class}.{Method}`, описание — из атрибута метода, дочерние узлы — вызовы из тела. Узел-класс в дерево
не добавляется.

Правило распространяется на вызовы внутри тела: `AnalyzeMethod` получает символ класса-владельца корня
и для вызовов его методов вкладывает узел метода напрямую, без узла-класса. Для классовых корней символ
не передаётся, поэтому обёртка `IsSameClassCall` и связи «класс → метод» сохраняются. Иначе класс
с описанием становился бы компонентом диаграммы метода, а связи от него — вторым корнем.

Альтернатива — обёртка `InvocationTree` с именем класса и единственным дочерним узлом метода —
отклонена: на диаграмме появился бы компонент класса, которого нет в разметке как корня, а содержимое
диаграммы совпало бы с диаграммой класса, что противоречит смыслу «отдельный компонент-метод».
Дополнительно обёртка даёт лишнюю пару «класс → метод» в слиянии, где класс без описания был бы
прозрачным, но сама конструкция усложняет модель без выгоды.

### D2. Использовать существующий `AnalyzeMethod` для корня

Корневое дерево метода — прямой результат `_methodAnalyzer.AnalyzeMethod(new ClassMethod(class, method),
currentDepth: 0, ct)`. Это тот же вызов, которым пользуется классовый корень для своих методов, поэтому
описание, признаки `IsSameClassCall` и обход вызовов не дублируются.

Альтернатива — построить новый `InvocationTree` по `ClassMethod.Name` и перенести `Invocations` из
результата `AnalyzeMethod` — отклонена: копирование теряет описание и флаги, а логика обхода начинает
зависеть от двух мест.

Семантика `maxDepth` не меняется: корневой метод анализируется с глубиной `0`, как методы корневого
класса. При `maxDepth: 0` диаграмма корневого метода содержит только сам метод.

### D3. Сбор корней-методов — по объявлениям внутри классов

Перебор идёт по `AllClasses`: для каждого `ClassDeclarationSyntax` берутся
`Members.OfType<MethodDeclarationSyntax>()`, символ метода разрешается через существующий
`SemanticModel` и расширение `GetC4ComponentAttribute()`, корнем считается метод с
`IsRootC4Component()`. Видимость не фильтруется, поэтому приватные методы тоже становятся корнями.

Следствия: методы интерфейсов, локальные функции и top-level statements корнями не становятся (их нет
в `AllClasses`); новые Roslyn API не нужны.

### D4. Класс и метод — два независимых корня

Перечисление отдаёт деревья классовых корней и деревья корней-методов независимо: без слияния,
дедупликации и без взаимного подавления. Порядок выдачи не является контрактом (как и порядок строк в
`.puml`).

Альтернатива — не создавать диаграмму класса, если в нём есть корневой метод, — отклонена: это скрывает
часть модели и ломает совместимость (разметка метода молча меняла бы существующую диаграмму класса).

### D5. Имя файла не требует правок CLI

`C4Builder` формирует путь как `{invocationTree.NodeName}.{extension}`, а для корня-метода `NodeName`
уже равен `{Class}.{Method}`. Поэтому правок в `C4ModelBuilder.Cli` нет; меняется только версия
инструмента, так как набор выходных файлов — наблюдаемое поведение.

### D6. Версионирование

`C4ModelBuilder.Attributes` не меняется: `AttributeTargets.Method` и параметр `isRoot` объявлены
раньше, сигнатуры и семантика конструктора те же. `C4ModelBuilder.Cli` получает подъём версии по
правилу AGENTS.md («правка поведения CLI поднимает CLI и не двигает атрибуты»).

### D7. Проверка — на модели `InvocationTree`

Тесты анализатора работают с in-memory `AdhocWorkspace`: проверяются имена корней (`Is.EquivalentTo`),
состав узлов (`Is.SupersetOf`, `Does.Not.Contain`), описания узлов и влияние `maxDepth`. Побайтовые
сравнения `.puml` не применяются — порядок компонентов и связей не контрактен.

## Risks / Trade-offs

- Двойной анализ метода, который помечен корнем и входит в корневой класс → только стоимость анализа;
  кэш не вводим, на наблюдаемое поведение не влияет.
- Рост числа файлов пропорционально числу помеченных методов → управляется разметкой; ограничение
  описано в README.
- Коллизия `{Class}.{Method}` из разных пространств имён → последний файл затирает предыдущий; правило
  совпадает с одноимёнными классами и зафиксировано сценарием спеки.
- Дублирование содержимого диаграмм класса и метода → ожидаемое следствие D4; фиксируется в README.
- Разметка `isRoot` на методе интерфейса по-прежнему молча игнорируется → вынесено в Non-Goals;
  отмечается в AGENTS.md как известная точка внимания.

## Migration Plan

Миграция данных не требуется. Выпуск: подъём `<Version>` в `C4ModelBuilder.Cli.csproj` → коммит → тег
`cli-vX.Y.Z` → диспатч `publish-cli-docker.yml` (порядок из AGENTS.md). Откат — реверт коммита;
поведение классовых корней не менялось, поэтому прежняя разметка даёт прежний результат.
