# Design

## Context

Мотивация — в `proposal.md` (Why). Текущее состояние и ограничения, определяющие подход:

- `.github/workflows/` содержит два workflow, оба с триггером `workflow_dispatch`:
  `publish-attributes-nuget.yml` (собирает и пакует только
  `C4ModelBuilder.Attributes.csproj`) и `publish-cli-docker.yml` (собирает образ только из
  `C4ModelBuilder.Cli.csproj`). Ни один не вызывает `dotnet test`: тестовых проектов нет ни в
  графе `C4ModelBuilder.Attributes.csproj`, ни в графе `C4ModelBuilder.Cli.csproj`.
- Публикующие джобы — `publish` (пакет в NuGet) и `build-and-push` (образ в `ghcr.io` с
  тегом `latest`); обе запускаются только вручную, поэтому сейчас ни один релиз не проходит
  через тесты.
- Решение `C4ModelBuilder/C4ModelBuilder.sln` — единственная точка входа, охватывающая
  тестовые проекты `C4ModelBuilder.Analyzer.Tests` и `C4ModelBuilder.PlantUmlCreator.Tests`.
- Тесты анализатора строят сценарии в памяти через `AdhocWorkspace` (без `MSBuildWorkspace`,
  без файлового ввода-вывода и сети), тесты рендера работают с моделями и строками —
  набор платформо-независим.
- `.editorconfig`: для `*.yml` — отступ 2 пробела, для всех файлов — UTF-8 с BOM, CRLF,
  без завершающих пробелов, максимум 140 символов.
- Сборка Release даёт три предупреждения: `CA1502` и `CA1506` в `MethodAnalyzer`
  (живые, не подавленные) и `CA1812` в CLI.
- Границы слоёв Models / Analyzer / PlantUmlCreator не затрагиваются: ни один файл C#,
  ни одна публичная сигнатура и ни одна спека не меняются.

## Goals / Non-Goals

**Goals:**

- Тесты решения запускаются автоматически на `push` в `main` и на каждом `pull_request`.
- Покраснение тестов видно на PR до мерджа, а не постфактум на `main`.
- Прогон в CI воспроизводим локально теми же тремя командами по тому же пути решения.
- Публикация пакета и образа невозможна без зелёного прогона тестов.

**Non-Goals:**

- Обход гейта: возможности опубликовать пакет или образ при красных тестах не
  предусматривается.
- Содержимое публикуемых артефактов: версия пакета, теги образа и шаги `dotnet pack` /
  `docker/build-push-action` не меняются.
- Любые проверки процесса OpenSpec (`openspec validate`) в CI.
- Версии SDK, покрытие, E2E-смоук CLI, смена политики предупреждений.

## Decisions

### 1. Новый `ci.yml` как точка входа проверки; публикаторы получают джобу тестов

Проверка на `push` / `pull_request` живёт в отдельном `ci.yml` по тому же пути решения, что и
локальный прогон (см. Context): публикующие workflow собирают только свои проекты и тестовых
проектов не видят. Публикаторы дополняются собственной джобой тестов (Decision 4): правка
существующих workflow не заменяет входную точку, а обеспечивает второе, релизное условие
запуска тестов.

### 2. Раннер `ubuntu-latest`, SDK `8.0.x`

Совпадает с существующими workflow и с базовым образом в `Dockerfile`. Поскольку тесты
платформо-независимы (см. Context), `windows-latest` не даёт дополнительного покрытия за
счёт более медленного и дорогого раннера. SDK `8.0.x` соответствует `TargetFramework`
всех проектов решения.

### 3. Конфигурация Release и раздельные шаги

В Release собираются релизные артефакты, поэтому гейт должен проверять именно её, а не
Debug. Шаги разделены и связаны флагами: `dotnet restore` →
`dotnet build --configuration Release --no-restore` →
`dotnet test --configuration Release --no-build`. Это исключает повторную сборку внутри
`dotnet test` и делает падение сборки отдельным, однозначно читаемым шагом.
Проверено локально: `build -c Release` — 0 ошибок, `test -c Release --no-build` — 42/42.

### 4. Гейт публикации: джоба тестов внутри каждого публикующего workflow

В `publish-attributes-nuget.yml` и `publish-cli-docker.yml` добавляется джоба тестов
(`checkout` → `setup-dotnet` → `restore` → `build --configuration Release` →
`test --configuration Release --no-build` по решению), а публикующие джобы (`publish`,
`build-and-push`) получают `needs` на неё. Публикация при красных тестах становится
невозможной, обхода в виде «принудительной публикации» не предусматривается.

Альтернативы: переиспользуемый `tests.yml` с `workflow_call`, подключаемый из трёх мест
(меньше дублирования, но лишний файл и indirection), и один `ci.yml` с четырьмя триггерами,
включая `workflow_call` (файлов меньше, но воркфлоу-«библиотека» смешивается с точкой входа, и
его `concurrency` начинает действовать в контексте релиза). Выбран вариант с дублированием
шагов: цена — три копии одной тройки команд, зато нет indirection, и релизные workflow
остаются самодостаточными; границы дублирования — три команды по одному и тому же пути
решения (см. Risks).

### 5. Отмена прогонов (`concurrency`) — только в `ci.yml`

`concurrency` с `cancel-in-progress: true` объявляется только во входной точке (`ci.yml`,
группа `${{ github.workflow }}-${{ github.ref }}`). Повторные пуши в один PR отменяют
устаревшие прогоны, но релизный прогон не может быть отменён другим запуском: в публикующих
workflow блок `concurrency` не добавляется, поэтому уже идущая публикация не прерывается
внезапно.

### 6. Предупреждения остаются предупреждениями

`-warnaserror` (или `TreatWarningsAsErrors` в CI) немедленно покрасил бы `main` из-за
`CA1502`, `CA1506` и `CA1812`; чистка этих предупреждений — самостоятельная задача и в
объём не входит.

## Risks / Trade-offs

- [Проверка на PR не блокирует мердж, пока в настройках репозитория не включён required
  status check] → шаг настройки GitHub вне диффа; зафиксирован в `proposal.md`
  («Не входит в объём»).
- [Три предупреждения в логе CI выглядят как шум] → принято осознанно, чистка отдельно.
- [Красные или флаки тесты блокируют релиз] → так и задумано: обхода у гейта нет, лечится
  исправлением тестов и повторным запуском публикующего workflow.
- [Шаги тестов продублированы в трёх файлах и могут разойтись] → митигация: везде одна и та же
  тройка команд по одному и тому же `.sln`, сверка блоков `run` при ревью; вынос в
  переиспользуемый workflow описан как отвергнутая альтернатива в Decision 4.
- [Гейт нельзя проверить холостым прогоном публикующего workflow] → диспатч реально публикует
  пакет в nuget.org и тег `latest` в `ghcr.io`; порядок джоб подтверждается сверкой графа на
  первом намеренном релизе, а работоспособность самих тестов — прогоном `ci.yml` на ветке.
- [Тесты идут ~10–20 с, но зависят от Roslyn, чувствительного к версии SDK] → версия
  закреплена на `8.0.x`; отсутствие `global.json` отмечено как риск, пин вне объёма.
- [Джоба запускается на `push` в `main`, то есть после мерджа] → основную защиту даёт
  триггер `pull_request`; `push`-триггер закрывает прямые коммиты и ручной запуск.
