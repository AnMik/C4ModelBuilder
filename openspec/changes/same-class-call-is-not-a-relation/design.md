## Context

Сейчас `MethodAnalyzer` для вызова метода своего класса создаёт узел-обёртку класса (ветка вызова
без получателя-поля), а `InvocationTreeMerger` строит связи по правилу «ближайший компонент-предок →
компонент» и подавляет только связь компонента с самим собой (`nearestComponentAncestor !=
signature`). Метод размечен `[C4Component]`, поэтому узел-обёртка не схлопывается, ближайшим
компонентом-предком для него становится метод, и в `.puml` попадает связь «метод → класс». Мотивация
— `proposal.md`; требования — дельта-спека `specs/component-diagram-generation/spec.md`.

Границы слоёв: `C4ModelBuilder.Models` ← (`C4ModelBuilder.Analyzer`, `C4ModelBuilder.PlantUmlCreator`),
`Analyzer` и `PlantUmlCreator` не ссылаются друг на друга, поэтому признак из анализатора обязан
попасть в генератор только через модель в `Models/Analysis`.

Проверяемый факт, на который опирается решение: для методов без описания вызов внутри класса уже
сегодня не даёт связи вообще — `InvocationTreeMergerTests.
Merge_internal_call_to_the_same_component_does_not_produce_a_self_relation` утверждает пустой
`diagram.Relations`, а `Merge_internal_call_to_the_same_component_still_relates_the_component_to_
downstream_components` — связь от класса к downstream-компоненту. Цикл появляется только у
размеченного метода.

## Goals / Non-Goals

**Goals:**

- Убрать связь «вызвавший метод → класс», сохранив вызов на диаграмме: связь SHALL идти от
  вызывающего метода к вызванному.
- Сохранить принадлежность методов классу: класс остаётся компонентом-предком своих методов
  (`ClassX → ClassX.MethodA`, `ClassX → ClassX.MethodB`).
- Сделать изменение публичной модели аддитивным: существующие вызовы `new InvocationTree(name,
  description)` продолжают компилироваться.
- Покрыть поведение NUnit-тестами на наблюдаемый вывод, включая текст `.puml`.

**Non-Goals:**

- Дублирование вхождения компонента на диаграмме и вложенная отрисовка (boundary-рамки).
- Изменение правил схлопывания узлов без описания, дедупликации связей и типизации компонентов.
- Подавление циклов, проходящих через другие компоненты.

## Decisions

**1. Признак ставит анализатор, а не генератор.** Узел-обёртка получает признак «вызов метода своего
класса», если вызывающий и вызываемый методы принадлежат одному классу (сравниваются символы классов:
`SymbolEqualityComparer`) в момент создания обёртки. Сравнение по символам, а не по простому имени,
исключает ложное срабатывание для одноимённых классов из разных пространств имён.

Альтернативы: вывод признака в `InvocationTreeMerger` из имён узлов (класс как родитель узла
`ClassX.<Метод>`) — отвергнуто как хрупкое: имя перестало бы быть только отображением. Проверка в
`InvocationTreeMerger`, что алиас встречался среди компонентов-предков на текущем пути — отвергнуто:
текущий обход (`Stack<(узел, nearest)>`) не хранит выход из узла, и правило оказалось бы шире
необходимого, гася настоящие взаимные зависимости (`ClassX → UserRepository → ClassX`).

**2. Признак живёт в `InvocationTree` как аддитивное `init`-свойство.**
`public bool IsSameClassCall { get; init; }` (имя выбрано при реализации), конструктор и
остальные члены не меняются.

Почему так: `Models/Analysis` — единственный разрешённый канал данных между анализом и рендером, а
`init`-свойство не трогает публичную подпись конструктора, поэтому существующий код потребителей и
тестов компилируется без правок. Альтернативы: необязательный параметр конструктора — меняет
публичную подпись; словарь признаков в генераторе — состояние вне модели и обход публичного
пайплайна; отдельный тип узла — лишняя сущность ради одного флага.

**3. Совпадение классов, а не ролей узлов.** Сравниваются классы вызывающего и вызываемого методов.
Это покрывает обе формы возврата: прямой вызов метода своего класса и вызов через самоссылочное поле
или интерфейс, реализованный тем же классом. Возврат через другой компонент признак не получает —
обёртка там создаётся внутри метода этого компонента, поэтому цикл вида
`ClassX → UserRepository → ClassX` остаётся на диаграмме.

**4. Помеченный узел прозрачен для связей и остаётся владельцем содержимого.** В блоке обработки
узла-компонента для помеченного узла связь «ближайший компонент-предок → узел» не добавляется,
вместо неё добавляется связь «ближайший компонент-предок → компонент вызванного метода» (прямой
ребёнок обёртки, если он компонент), а переустановка `nearestComponentAncestor = signature`
сохраняется:

```csharp
if (node.C4ComponentDescription != null)
{
    components.Add(signature);
    descriptions[signature] = node.C4ComponentDescription;

    if (node.IsSameClassCall)
    {
        // Обёртка своего класса: концом связи становится вызванный метод, а не класс.
        foreach (var child in node.Invocations.Where(child => child.C4ComponentDescription != null))
        {
            if (nearestComponentAncestor != null && nearestComponentAncestor != child.NodeName)
            {
                relations.Add((From: nearestComponentAncestor, To: child.NodeName));
            }
        }
    }
    else if (nearestComponentAncestor != null && nearestComponentAncestor != signature)
    {
        relations.Add((From: nearestComponentAncestor, To: signature));
    }

    nearestComponentAncestor = signature;
}
```

Для дерева `ClassX → ClassX.MethodA → ClassX (помечен) → ClassX.MethodB` это даёт связь
`ClassX.MethodA → ClassX.MethodB` (прозрачность) и, благодаря переустановке владельца, ещё и
`ClassX → ClassX.MethodB` (принадлежность). Почему ребёнок, а не вся цепочка: у обёртки ровно один
ребёнок — вызванный метод; если он не компонент, связь не создаётся вовсе и поведение совпадает с
сегодняшним для методов без описания.

Альтернатива (рассмотрена и отвергнута: splice) — не создавать обёртку, а подвешивать вызванный метод
прямо под вызывающий: дало бы `ClassX → ClassX.MethodA → ClassX.MethodB` без связи
`ClassX → ClassX.MethodB`, то есть потерю принадлежности для транзитивно вызванных методов.

**5. Дублирование вхождения компонента отвергнуто.** Вариант `ClassX → MethodA → ClassX₂ → MethodB`
не берём, потому что: (1) alias — идентификатор компонента и в модели, и в тексте, поэтому второе
появление требует синтетических alias и сущности «вхождение» вместо `HashSet` компонентов и
`HashSet<(From, To)>` связей; (2) нумерация вхождений зависит от порядка обхода `HashSet`, а он между
запусками меняется — нестабильный текст и дрожащие тесты; (3) вхождений столько, сколько путей, а не
классов, поэтому у класса с несколькими размеченными методами диаграмма разрастётся; (4) читатель
видит два разных компонента с одинаковым именем; (5) информационного выигрыша нет: повторный узел
класса воспроизводит связь «метод → класс» и не называет вызванный метод.

**6. Пример целевого проекта расширяется.** `AdminController.SendPromoAsync` вызывает приватный метод
своего класса; сквозная проверка — `scripts/Invoke-Sample.ps1`. Это единственное место, где новое
поведение видно глазами: юнит-тесты работают на моделях, а `.puml` в репозитории не хранится.

## Risks / Trade-offs

- [Новое ребро «метод → метод» читается как зависимость между компонентами] → принято: методы
  размечены `[C4Component]` и на диаграмме являются компонентами, поэтому связь корректна и называет
  то, что происходит; принадлежность выражена отдельной связью от класса.
- [Поведение размеченных и неразмеченных методов расходится] → проверено: при неразмеченном вызванном
  методе связь не создаётся (задача 2.4), при неразмеченном вызвавшем связь идёт от класса, как и
  сегодня; регрессом служат `Merge_internal_call_to_the_same_component_*` и
  `Generator_internal_calls_inside_a_component_do_not_render_self_relations`.
- [Расширение примера меняет ожидания тестов анализатора] → обновление ожиданий для `AdminController`
  входит в тот же коммит.
- [Дублирование как «очевидное» решение вернётся при ревью] → причины отказа записаны в п. 5 и в
  `proposal.md`, раздел «Не входит в объём».
- [Регрессия в тексте `.puml` не видна на уровне модели] → тест генератора проверяет и наличие
  `Rel(<класс>, <метод>, "")`, и отсутствие `Rel(<метод>, <класс>, "")`.
- [Изменяется наблюдаемое содержимое `.puml`] → дельта спеки `component-diagram-generation` входит в
  это же изменение; ранее сгенерированные файлы при повторном запуске отличаются, но порядок строк и
  содержимое `output/` контрактом не считаются (см. `proposal.md`).

## Open Questions

- Имя признака — решено при реализации: `IsSameClassCall`. Отклонённые варианты
  (`IsReturnToEnclosingClass`, `ReturnsToOwner`) описывают «возврат», тогда как признак отмечает вызов
  метода своего класса; на спеки, подход и разбиение задач выбор имени не влиял.
