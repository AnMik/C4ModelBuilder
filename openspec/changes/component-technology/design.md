# Design

## Context

См. `proposal.md` — «Why». Ниже только то, что определяет подход.

Текущее состояние, существенное для решений:

- `C4ComponentAttribute` (`netstandard2.1`, дефолтный C# 8: блочные namespace, без `ImpliedUsings`)
  принимает `(string description, bool isRoot = false)`, оба свойства — только для чтения.
- Анализатор читает атрибут из `AttributeData` позиционно:
  `IsRootC4Component => ConstructorArguments is [_, { Value: true }, ..]`,
  `GetC4ComponentDescription => ConstructorArguments is [{ Value: var value }, ..]`.
- Пайплайн: `InvocationTree` (Models) → `InvocationTreeMerger` (схлопывание) → `C4ComponentDiagram`
  (internal) → `PlantUmlRenderer` (текст). `Analyzer` и `PlantUmlCreator` друг на друга не ссылаются.
- Значение описания `null` означает «узел не компонент»; пустая строка `""` — компонент с пустым
  описанием. Это различение держится на `C4ComponentDescription != null` в слиянии и трогать его нельзя.
- Корневой метод строится с `excludedClassSymbol`: класс-владелец в его дерево не попадает.

Проверенный факт о библиотеке (plantuml-stdlib, `C4_Component.puml` → `C4_Container.puml` →
`C4_Context.puml` → `C4.puml`):

```plantuml
!unquoted procedure Component($alias, $label, $techn="", $descr="", $sprite="", $tags="", ...)
!function $getElementBase($label, $techn, $descr, $sprite)
  '== label' + '\n//[techn]//' + '\n\n' + descr
```

Третий позиционный аргумент — технология (курсив в квадратных скобках), четвёртый — описание (блок).
Отдельно важно, что `$toElementArg` подставляет технологию из цветового тега только тогда, когда явная
технология не задана. После этого изменения тег перестаёт конкурировать с технологией за этот слот: тег
теперь **выводится из** технологии, а не существует независимо от неё, поэтому конфликта быть не может —
маркер `[technology]` всегда один и определяется значением технологии.

## Goals / Non-Goals

**Goals:**

- Провести технологию по всем трём слоям, не нарушив их односторонние зависимости.
- Поставить описание в слот описания, а технологию — в слот технологии.
- Сохранить существующее различение «`null` — не компонент, `""` — компонент без описания».
- Не менять способ, которым анализатор читает описание и `isRoot`.

**Non-Goals:**

- Автовывод технологии и изменение набора цветовых тегов и их цветов.
- Экранирование кавычек в значениях (существующий пробел).
- Наследование технологии от класса к методу.

## Decisions

### D1. Форма макроса: `Component(alias, name, technology, description)`

Описание переносится в четвёртый аргумент, технология занимает третий. При отсутствии технологии
выводится `""` — плейсхолдер обязателен, иначе описание снова уедет в слот технологии.

**Почему:** только так технология и описание получают то оформление, которое для них предусматривает
C4-PlantUML.

**Альтернатива:** оставить описание третьим аргументом, а технологию передавать именованным
`$techn="…"`. Отклонено: закрепляет ошибку навсегда и делает разбор `.puml` неоднозначным.

**Цена:** внешний вид всех существующих диаграмм меняется (описание перестаёт быть курсивной строкой в
скобках). Это осознанный **BREAKING** текста диаграммы.

### D2. Технология задаётся третьим параметром конструктора

`C4ComponentAttribute(string description, bool isRoot = false, string? technology = null)`, свойство
`Technology` — только для чтения.

Рассмотренные варианты:

| Вариант | Плюсы | Почему отклонён |
| --- | --- | --- |
| Третьим параметром (выбран) | Одна сигнатура; свойство неизменяемое, как остальные; технология сочетается с `isRoot`; все существующие вызовы компилируются | — |
| Settable-свойство `Technology { get; set; }` | Не меняет метаданные конструктора | Свойство становится изменяемым после создания, вразрез с `Description`/`IsRoot`; `init` недоступен — проект на C# 8 (`CS8400` + отсутствие `IsExternalInit` проверены) |
| Перегрузка `(string description, string technology)` | Старый токен конструктора сохраняется | Технологию **невозможно** поставить на корневой компонент: `("x", "T", isRoot: true)` даёт `CS1744`, `("x", isRoot: true, technology: "T")` — `CS1739`. Корни — главные компоненты диаграммы, терять их разметку нельзя |
| Вторым параметром, до `isRoot` | Красивее позиционно | `[C4Component("X", true)]` перестаёт компилироваться → мажорная версия 4.0.0 |

**Следствие:** старый токен конструктора исчезает. Разметка пересобирается без правок, но потребитель,
собранный против 3.0.0 и не пересобранный, получит ошибку при инстанцировании атрибута. Для этого
инструмента сценарий практически не встречается: анализ идёт по исходникам через `MSBuildWorkspace`, и без
пересборки целевого проекта диаграмма не изменится. Спека формулирует совместимость в терминах компиляции
разметки, а добавление необязательного параметра её не нарушает, поэтому выпускается минорная версия
`3.1.0`, а не мажорная. Компенсировать разрыв нечем: технология должна сочетаться с `isRoot` на одном
атрибуте, а `{ get; set; }` недоступен из-за C# 8 в проекте атрибутов и нарушает неизменяемость свойств.

### D3. Чтение технологии — новый extension, существующие не трогаем

`GetC4ComponentTechnology()` читает `ConstructorArguments[2]`. `IsRootC4Component` и
`GetC4ComponentDescription` остаются как есть.

**Почему:** проверено на in-memory компиляции — при опущенном необязательном параметре Roslyn всё равно
материализует значение по умолчанию в `ConstructorArguments` (`["plain", False, null]`), поэтому
позиционное чтение остаётся корректным, а лишние правки создают риск регрессии в поведении `isRoot`.

### D4. Технология переносится полем, а не наследуется

`InvocationTree` получает третий необязательный параметр конструктора и свойство
`C4ComponentTechnology`; `InvokedMethod` — пару `ClassTechnology`/`MethodTechnology` по образцу
`ClassDescription`/`MethodDescription`.

**Почему:** три необязательных параметра в `InvocationTree` с сохранением порядка (после
`c4ComponentDescription`) не ломают существующие вызовы в тестах. Отсутствие наследования от класса к
методу повторяет поведение описания и не требует исключений в правилах.

**Альтернатива:** наследование технологии методом от класса отклонено — размножает метку по всем узлам и
расходится с тем, как ведёт себя описание.

### D5. Технология не участвует в идентичности компонента

Схлопывание по-прежнему дедуплицирует по `NodeName`. Технология — атрибут отображения.

**Почему:** два узла с одним именем и разными технологиями не должны становиться двумя компонентами —
это развалило бы существующую модель связей.

### D6. `C4ComponentDiagram.C4Component` получает `Technology` в конец

Поле добавляется после `Type`, чтобы существующие позиционные конструкции в тестах компилировались без
правок, а рендерер подставлял `null`/`""` в третий аргумент.

**Почему в конец:** иначе пришлось бы править все вызовы конструктора в тестах, не меняя поведения; поле
необязательное и хранится в модели отдельно от `Type`, хотя значение `Type` теперь выводится из технологии
(D7).

### D7. Цветовой тег выбирается по технологии

`ResolveComponentType` перестаёт смотреть на имя компонента и сравнивает технологию: подстрока
`Repository` (без учёта регистра) раньше `Gateway`, иначе тег не выводится. Члены перечисления `Type`
(`Normal`/`Repository`/`Gateway`) сохраняются как имена тегов, меняется только источник значения.

**Почему:** технология теперь единственный способ сказать, что это за компонент; правило по подстроке в
имени перестаёт отражать реальность и даёт ложные срабатывания на классе `OrderRepository` без технологии.
Сравнение по подстроке сохранено, чтобы не вводить словарь технологий: `"EF Core Repository"` даёт
`repository`, `"Kafka Gateway"` — `gateway`.

**Альтернатива:** удалить типизацию целиком (вместе с `AddElementTag` и цветами). Отклонено: теряется
цветовое кодирование, которое уже используют существующие диаграммы.

**Следствие для слоёв:** технология теперь нужна `InvocationTreeMerger` для выбора тега, а не только
рендереру — поле обязано доехать до модели диаграммы, что D6 и обеспечивает. `InvocationTreeMerger` при
этом по-прежнему не обращается к `Analyzer`.

## Risks / Trade-offs

- **Внешний вид всех существующих диаграмм меняется** → принять осознанно: это и есть исправление
  D1; зафиксировать в proposal как **BREAKING** и в дельте спеки. Раскатка — мажорный релиз
  CLI `2.0.0`.
- **Существующие диаграммы теряют цвет** там, где компонент полагался на имя (`OrderRepository` без
  технологии больше не зелёный) → это ожидаемое следствие D7: разметка должна явно назвать технологию.
  Указать в README как часть миграции.
- **Не пересобранный потребитель атрибутов падает на инстанцировании** → осознанно принято: анализ идёт
  по исходникам, поэтому без пересборки целевого проекта диаграмма не изменится. Обосновано в D2 и в
  proposal; страхует будущий мажорный релиз пакета, отдельного механизма не вводим.
- **Плейсхолдер `""` легко потерять при будущей правке рендерера** → закрепить тестом на компонент без
  технологии, где проверяется позиция описания, а не только его наличие.
- **Пустая технология и отсутствующая технология визуально неотличимы** (`""` в обоих случаях) →
  приемлемо: C4-PlantUML при пустой технологии просто не рисует строку, а различать их в тексте
  диаграммы незачем.
- **Технология с кавычкой внутри ломает `.puml`** → существующий пробел, общий с описанием; в объём не
  входит.

## Migration Plan

Единый PR: атрибуты `3.1.0`, CLI `2.0.0`, дельта-спеки синкаются и change архивируется до мерджа.
Порядок внутри PR — снизу вверх по слоям (Attributes → Models → Analyzer → PlantUmlCreator → тесты →
документация → версии), чтобы сборка оставалась зелёной на каждом шаге. Откат — revert коммита:
формат диаграммы и версия пакета меняются вместе, обратная совместимость по тексту не поддерживается.

Пара версий — CLI `2.0.0` вместе с атрибутами `3.1.0` — фиксируется как соглашение о релизе и
указывается в README. Ребра графа зависимостей между ними нет и не появляется: CLI публикуется образом,
получает атрибуты транзитивно через ссылку на анализатор, а версия образа берётся из `<Version>` в
`C4ModelBuilder.Cli.csproj`.
