# C4ModelBuilder

Инструмент для автоматической генерации PlantUML C4 диаграммы компонентов на основе разметки специальными атрибутами c# репозитория.

Поведение публичного контракта — атрибуты разметки, параметры CLI и содержимое диаграммы — зафиксировано спеками в `openspec/specs/`.

## Разметка

На первом этапе нужно разметить атрибутами целевой проект.
Разметка проекта осуществляется атрибутами из проекта [C4ModelBuilder.Attributes](C4ModelBuilder/C4ModelBuilder.Attributes/README.md).

Сейчас поддерживается только C4-уровень 3 (Component) — атрибут `C4Component`;
остальные атрибуты (`C4Context`, `C4Container`, `C4Code`) объявлены, но не обрабатываются.

У компонента два текстовых поля: обязательное описание и необязательная технология.

```csharp
[C4Component("Главная страница", isRoot: true, technology: "ASP.NET Core")]
public sealed class HomeController
{
}

[C4Component("Хранилище заказов", technology: "EF Core Repository")]
public sealed class OrderRepository
{
}
```

Технология выводится на диаграмме курсивом в квадратных скобках под названием компонента, описание —
блоком ниже. Если технология не задана, её строка не рисуется.
Технология класса и технология метода независимы: метод не наследует технологию своего класса.

## Построение схемы

На втором этапе нужно запустить анализ целевого проекта с помощью консольного приложения.
Пример вызова CLI для примера целевого проекта:

```powershell
./scripts/Invoke-Sample.ps1
```

### Как элементы попадают на диаграмму

1. Точки входа — компоненты с `[C4Component("…", isRoot: true)]`:
   - **класс** — корень `{класс}`: анализируются только его **публичные методы**;
   - **метод класса** — корень `{класс}.{метод}`: анализируется сам метод, независимо от видимости;
     класса-владельца на такой диаграмме нет.
2. Корней может быть несколько; интерфейсы как root не поддерживаются.
3. Если `isRoot` стоит и на классе, и на его методе, строятся две независимые диаграммы: корень-класс
   не заменяет корень-метод, а корень-метод не схлопывает диаграмму класса.
4. Каждый корневой компонент даёт отдельный файл в каталоге `--output`: `{класс}.puml` для класса и
   `{класс}.{метод}.puml` для метода. Одноимённые корни из разных пространств имён пишутся в один файл —
   содержимое последнего затирает предыдущее.
5. Глубина `--max-depth` отсчитывается от корня: для корня-класса — от его методов, для корня-метода —
   от самого метода. При глубине `0` на диаграмме остаётся только корневой узел.
6. Поддерево вызовов строится из текущего метода по вызовам методов **полей** текущего класса.
7. Компонентом диаграммы становится узел дерева, у которого атрибут `[C4Component]` имеет
   **заданное описание** (значение `""` — тоже компонент, с пустым описанием).
8. Описание берётся от **класса**, а не от интерфейса.
9. Описание от интерфейса берётся только если класс-реализация не найден в решении.
10. Технология берётся по тем же правилам, что и описание: от класса-реализации, от интерфейса — только
    если реализации нет. От класса к методу технология не передаётся.
11. Цветовой тег компонента выводится из его технологии: подстрока `Repository` (без учёта регистра) даёт
    зелёный тег `repository`, подстрока `Gateway` — фиолетовый `gateway`; `Repository` проверяется раньше
    `Gateway`. Компонент без технологии тега не получает. Имя класса на выбор тега не влияет.
12. Узлы с описанием `null` на диаграмму не попадают — они используются только для построения промежуточного
    дерева вызовов.
13. Вызов метода своего класса (`ClassX.MethodA` вызывает другой метод того же класса) связывает вызывающий
    метод с вызванным (`ClassX.MethodA → ClassX.MethodB`). В диаграмме класса класс-владелец остаётся
    компонентом-предком обоих методов, а связь вызывающего метода с классом не создаётся. В диаграмме
    корня-метода класса-владельца нет, поэтому связь идёт от вызывающего метода к вызванному.
14. Вызовы CQRS через `Rds.Cqrs.Queries.IQueryService` / `Rds.Cqrs.Commands.ICommandProcessor` резолвятся
    в обработчики запросов.
15. Поля типов `IMapper` и `ITaggableCache` игнорируются.

## Параметры командной строки (CLI)

При запуске `C4ModelBuilder.Cli` поддерживаются следующие аргументы:

| Аргумент | Псевдоним | Тип | Обязательный | По умолчанию | Описание |
| - | - | - | - | - | - |
| `--solution` | `-s` | `FileInfo` | Да | — | Путь к целевому файлу решения (`.sln`). |
| `--output` | `-o` | `DirectoryInfo` | Да | — | Путь к директории для сохранения сгенерированных PlantUML-диаграмм. |
| `--max-depth` | `-d` | `int` | Нет | `15` | Максимальный уровень глубины рекурсии при анализе дерева вызовов. |
| `--output-type` | `-t` | `OutputType` | Нет | `Puml` | Тип выходного файла (`puml`). |
| `--project` | `-p` | `string` | Нет | Все проекты | Имя конкретного проекта решения для анализа. |
| `--exclude` | `-e` | `string` | Нет | — | Маска исключаемых из анализа проектов (например, `*tests` или `*Sample*`). |
| `--log-level` | `-l` | `LogLevel` | Нет | `Warning` | Минимальный уровень логирования (`Trace`, `Debug`, `Information`, `Warning`, `Error`, `Critical`, `None`). |

### Версия и справка

Флаги `--version`, `--help` и `-h` предоставляет библиотека разбора аргументов, поэтому в таблице
параметров их нет:

| Аргумент | Псевдоним | Описание |
| - | - | - |
| `--version` | — | Печатает версию инструмента и завершается с кодом `0`, не выполняя анализ. |
| `--help` | `-h` | Печатает справку с перечнем параметров и завершается с кодом `0`. |

`--version` нельзя сочетать с другими параметрами: `--version -s <решение> -o <каталог>` даёт сообщение об
ошибке и код `1`.

Версия CLI задаётся свойством `<Version>` в `C4ModelBuilder.Cli/C4ModelBuilder.Cli.csproj` и не связана с
версией контракта разметки (`C4ModelBuilder.Attributes`). Проверить версию локально:

```bash
dotnet run --project C4ModelBuilder/C4ModelBuilder.Cli/C4ModelBuilder.Cli.csproj -- --version
```

### Соответствие версий CLI и атрибутов

Версии двух артефактов поднимаются независимо, но поставляются парой: CLI `2.0.0` рассчитан на атрибуты
`3.1.0`, где появился параметр `technology`. Пакетной зависимости между ними нет: CLI поставляется образом
`ghcr.io`, а не NuGet-пакетом, и не объявляет `PackageReference` на `C4ModelBuilder.Attributes` — атрибуты
попадают в анализ из целевого решения. Поэтому соответствие зафиксировано соглашением, а не графом пакетов:
при выпуске CLI-версии, меняющей трактовку разметки, версия атрибутов указывается в описании релиза.

### Пример прямого запуска через `dotnet run`

```bash
dotnet run --project C4ModelBuilder/C4ModelBuilder.Cli/C4ModelBuilder.Cli.csproj -- -s "C4ModelBuilder/C4ModelBuilder.sln" -o "output" -d 16 -t puml -l Information
```

## Контейнерный образ

Workflow `publish-cli-docker.yml` читает версию из `<Version>` в `C4ModelBuilder.Cli.csproj` и публикует
образ с двумя тегами в `ghcr.io`: `X.Y.Z` (версия сборки) и `latest`. Повторный диспатч на уже
существующий тег его не перезаписывает — версию поднимают в `.csproj`.

Та же версия попадает в метки образа: `org.opencontainers.image.version`, `...revision` (SHA коммита) и
`...source` (URL репозитория). Локальная проверка:

```bash
docker build --build-arg VERSION=1.1.0 -t c4builder-cli:local .
docker inspect --format '{{index .Config.Labels "org.opencontainers.image.version"}}' c4builder-cli:local
docker run --rm c4builder-cli:local --version
```

## Структура репозитория

- `C4ModelBuilder.Attributes` - атрибуты для разметки целевого решения.
- `C4ModelBuilder.Cli` - консольный инструмент построения с4 диаграмм целевого решения.
- `C4ModelBuilder.Models` - общие модели.
- `C4ModelBuilder.Analyzer` - анализатор классов и связей целевого проекта.
- `C4ModelBuilder.PlantUmlCreator` - построитель диаграмм в формате plantuml на основе результатов анализа.
- `C4ModelBuilder.Sample.Target` - пример целевого проекта, размеченного атрибутами.
- `C4ModelBuilder.PlantUmlCreator.Tests` - тесты построителя диаграмм.
- `C4ModelBuilder.Analyzer.Tests` - тесты анализатора: собирают in-memory `Solution` (`AdhocWorkspace`).
- `scripts/Invoke-Sample.ps1` - запуск CLI на примере целевого проекта.
- `openspec/` - спеки (`specs/`), изменения (`changes/`) и конфигурация (`config.yaml`).
- `AGENTS.md` - контекст и правила для ИИ-агентов.
- `.github/workflows/` - `ci.yml` собирает и тестирует решение на push/PR; публикация
  `C4ModelBuilder.Attributes` в NuGet и CLI-образа в `ghcr.io` — только после прогона тестов.
- `Dockerfile` - образ CLI: внутри доступна команда `c4builder`, базовый образ на .NET 8 SDK.

### Разработка

- NuGet-пакет `C4ModelBuilder.Attributes` собран под `netstandard2.1`.

Требования:

- .NET 8 **SDK**: анализ решения выполняется через Roslyn `MSBuildWorkspace`.
- `npm` (опционально): только для OpenSpec-воркфлоу.

Файлы интеграции с ИИ-агентами (`.cline/skills/`, `.clinerules/`, `.dsh/skills/`,
`.opencode/commands/`, `.opencode/skills/`) в git не хранятся, поэтому локально нужно выполнить:

```bash
npm i -g @fission-ai/openspec@1.13.0
openspec init --tools cline
```

Конвенции кодирования заданы в [.editorconfig](.editorconfig). Архитектурные границы и дисциплина тестов описаны в `AGENTS.md`.
